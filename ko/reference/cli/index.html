CLI 레퍼런스

BomLens의 전체 옵션과 분석 모드, CI/CD 통합 방법, 트러블슈팅을 설명합니다.

옵션 레퍼런스

Section titled “옵션 레퍼런스”

Windows 사용자: 위 명령은 macOS/Linux 기준입니다. 다음 중 하나를 고르세요. 설치는 시작하기를 참고하세요.

  • ./scripts/scan-sbom.sh를 scripts\scan-sbom.bat로 바꿔 실행합니다 (Git Bash 필요).
  • WSL2에서는 명령을 그대로 실행합니다.
  • CLI 없이 쓰려면 scripts\sbom-ui.bat을 더블클릭하거나 데스크톱 앱을 내려받으세요.
옵션 기본값 설명
--project <이름> — (필수) 프로젝트 이름
--version <버전> — (필수) 프로젝트 버전
--supplier <supplier> — 이 SBOM이 설명하는 제품의 공급자. "Name <https://...>"(url로 기록) 또는 "Name <email>"(연락처 email로 기록) 형식으로 쓰며, metadata.component.supplier에 기록한다. 이름 없이 "<https://...>"만 쓰면 URL만 기록하고, 앞뒤 공백을 지우고 빈 값이면 기록하지 않는다. metadata.supplier는 SBOM 작성자로 읽히므로 건드리지 않는다. 이름만 쓰면 기록은 하되 경고한다. bsi-tr-03183-2 검사 기준은 공급자의 URL이나 이메일을 요구하기 때문이다. --analyze에서는 공급사 SBOM을 그대로 두므로 기록하지 않는다. --target으로 준 Yocto 빌드 디렉터리는 같은 경로로 스캔하지만 그 SBOM은 이 스캔이 만든 것이므로 기록한다
--target <대상> 현재 디렉터리 분석 대상: 디렉터리(소스 트리, 또는 OS rootfs·빌드 산출물 staging), Docker 이미지, 바이너리 파일, .zip/.tar.gz 아카이브. Yocto 빌드 디렉터리는 그렇게 인식해서, 빌드 트리를 훑는 대신 tmp/deploy/images/ 아래에 빌드가 만든 이미지 SBOM을 분석합니다(공급사 SBOM 가이드 참고). 소스 트리가 아닌 폴더(최상위에 매니페스트, 잠금 파일, 빌드 파일이 없는 폴더)가 루트 파일시스템이나 펌웨어 이미지를 바로 아래에 하나만 담고 있으면(릴리스의 images/ 폴더 등) 그 루트 파일시스템이나 이미지를 분석하고, 그렇게 했다고 알려 줍니다. 펌웨어 이미지는 시그니처나 .bix, .trx 같은 펌웨어 확장자로 판단하며, .bin과 .img는 시그니처가 있어야 합니다. 최상위에 실행 파일, 공유 라이브러리, node_modules, 모델 파일이 있거나 최상위 파일이 20개를 넘는 폴더는 소스로 분석합니다. 여러 개를 담고 있으면 스캔을 멈추고 각각에 쓸 --target을 보여 줍니다
--git <url> — git/GitHub URL을 얕은 클론(shallow) 후 소스로 분석 (비공개 저장소: GIT_TOKEN 환경변수)
--branch <ref> 기본 브랜치 --git 대상의 브랜치, 태그, 커밋 (별칭 --ref)
--exclude <경로> — 소스 스캔에서 제외할 경로. 여러 번 지정할 수 있다. 경로는 스캔할 폴더 기준 상대 경로이다(예: --exclude vendor/legacy). 글롭, 절대 경로, ..은 거부한다. 제외한 경로를 뺀 사본을 스캔하므로 빌드, 라이선스 검사, 파일 트리가 모두 그 경로를 건너뛴다. 없는 경로는 알리고 무시한다
--firmware false --target 파일, 또는 빌드에서 나온 루트 파일시스템처럼 압축을 푼 이미지가 든 --target 폴더를 펌웨어 모드로 강제 (opt-in 펌웨어 이미지). 패키지 데이터베이스가 없는 루트 파일시스템 폴더는 펌웨어 이미지가 있으면 이 옵션 없이도 펌웨어 모드로 바뀐다
--as-source false 디렉터리 --target을 있는 그대로 소스 트리로 분석합니다. 폴더 안의 루트 파일시스템이나 펌웨어 이미지로 바꾸지 않고, Yocto 빌드 디렉터리와 루트 파일시스템도 따로 인식하지 않습니다. --firmware와 함께 쓸 수 없습니다
--analyze <sbom> — 공급사 SBOM 검증·분석 (별칭 --sbom). CycloneDX/SPDX. --target와 배타
--model <참조> — AI SBOM(CycloneDX 1.7 ML-BOM)을 생성한다. HuggingFace 모델 ID(조직/모델)는 OWASP AIBOM Generator로 처리한다(opt-in bomlens-aibom 이미지; 모델 카드 메타데이터를 네트워크로 가져옴). Figshare 항목은 페이지 주소나 DOI, 항목 번호로 주면 공개 항목 조회로 데이터셋으로 기술하며 계정도 별도 이미지도 필요 없다. 이름에 “figshare”가 없는 기관 DOI는 다른 DOI와 구분할 수 없으므로 항목 주소를 준다. HuggingFace 데이터셋은 datasets/<owner>/<name>, https://huggingface.co/datasets/<owner>/<name>(이름 뒤의 /tree/main 같은 부분은 무시), hf:<owner>/<name> 중 하나로 주면 기본 이미지에서 데이터셋으로 기술하며, 카드의 source_datasets에 적힌 데이터셋도 함께 읽는다(AIBOM_DATASET_DEPTH, AIBOM_DATASET_MAX_LOOKUPS). HuggingFace가 모델과 데이터셋에 같은 형식을 쓰므로 앞에 아무것도 붙이지 않은 owner/name은 항상 모델 id로 읽는다. 접근 제한이 있거나 비공개인 데이터셋은 HF_TOKEN이 필요하다. --target/--analyze/--git/--merge와 배타
--model-file <경로> — AI 모델 파일 하나를 읽어 그 헤더만으로 기술한다. GGUF, safetensors, PyTorch(.pt/.pth/.ckpt), pickle, npz, npy, ONNX를 인식한다. 오프라인으로 동작하고 HuggingFace 계정이 필요 없어 공개하지 않은 모델도 스캔할 수 있다. 채울 수 있는 정보는 형식마다 다르다. GGUF는 이름과 라이선스, 아키텍처를 담고 있지만 safetensors는 대개 텐서 정보만 있으며, 파일이 선언하지 않은 값은 추측하지 않고 비워 둔다. --target에 .gguf나 .safetensors, .pt 같은 경로를 주면 이 방식으로 읽는다. --target/--analyze/--git와 배타
--license <spdx-id> — 프로젝트를 배포하는 배포 라이선스(예: Apache-2.0). SBOM 루트 컴포넌트에 acknowledgement를 concluded(배포 라이선스)로 기록하고, 조건이 충돌하는 의존성을 표시하는 데 쓴다. 생성 도구가 읽은 루트 라이선스는 이 값으로 바꾼다. 소스 스캔으로는 알아낼 수 없어(cdxgen이 maven과 gradle에서 루트 라이선스를 비워 둔다) 지정하지 않으면 충돌 판정을 내리지 않는다. 대신 프로젝트 매니페스트에서 읽은 라이선스는 루트 라이선스가 비어 있을 때만 declared로 채운다. --analyze에서 공급사 SBOM이 적은 루트 라이선스는 덮어쓰지 않는다. --target으로 준 Yocto 빌드 디렉터리에서는 이미지에 기록한다. SPDX 라이선스 목록의 식별자(대소문자 무관)는 license.id로, LicenseRef-나 DocumentRef-...:LicenseRef- 이름(접두사 대소문자 무관)은 license.name으로, 표현식은 expression으로 적는다. 표현식은 SPDX 식별자와 LicenseRef- 이름을 AND나 OR로 잇고, WITH 뒤에는 SPDX 예외 식별자를 두며, 괄호가 짝을 이뤄야 한다. 연산자는 대소문자를 가리지 않고, 식별자는 SPDX 목록의 표기로 적는다. 그 밖의 값, 예를 들어 Proprietary 같은 자유 문구나 Proprietary or commercial, MIT AND 같은 표현식은 이유와 함께 거부하며, 자유 문구에는 대신 쓸 LicenseRef- 이름을 알려 준다. 이 값을 기록하는 스캔(소스 스캔, 루트 파일시스템, Yocto 빌드 디렉터리)에서는 누가 시작했든(CLI, 웹 UI, CI 작업) 스캔을 시작할 때, 아무것도 생성하기 전에 거부한다. CLI는 컨테이너를 시작하기 전에 거부한다. 프로젝트 매니페스트에서 읽은 라이선스가 맞지 않으면 경고와 함께 기록하지 않는다
--sbom-author <name> — 이 SBOM을 생성한 주체. 스캔을 실행하는 조직이나 사람을 가리키며, 도구도 소프트웨어를 만든 쪽도 아니다. metadata.authors에 정식 명칭으로 기록하고 약어는 쓰지 않는다. 스캔으로는 알아낼 수 없는 값이라 지정하지 않으면 자리표시자를 채우지 않고 필드를 빼 둔다. Name <email> 형식(예: "Example Corp <sbom@example.com>")으로 쓰면 bsi-tr-03183-2 검사 기준이 SBOM 작성자에게 요구하는 이메일도 함께 기록한다. --analyze에서는 기록하지 않지만, --target으로 준 Yocto 빌드 디렉터리는 이 스캔이 SBOM을 만들므로 기록한다
--ai-declare <file> — AI 모델이나 데이터셋 스캔에서, 스캔으로 읽을 수 없는 내용을 모델 공개자가 선언한 파일(JSON). 출시일, 모델과 데이터를 만든 주체, 학습과 평가에 쓴 데이터셋, 기반 모델 리비전, 배포 가중치 범위 같은 값이다. 선언한 값은 대부분 SPDX 3.0.1 AI 문서에만 반영한다. 예외는 모델을 실행하는 서비스(service)와 모델의 입력과 출력 종류, 학습 연산량, 적대적 시험 여부이며, 이 값들은 CycloneDX SBOM에도 발행자 선언으로 표시되어 들어간다(아래 예시 참고). 모든 AI 스캔이 시작점으로 쓸 빈 양식 {Project}_{Version}_ai-declaration.template.json을 만든다. 스캔에 없는 필드, 값, 데이터셋, 기반 모델을 적은 파일은 이유와 함께 거부하고, 문서는 선언 없이 초안으로 만든다. 받아들인 파일은 {Project}_{Version}_ai-declaration.json으로 보관하고 같은 버전을 다시 스캔할 때 다시 적용한다. --model, --model-file, --target 없이 이 옵션만 주면 허브 저장소나 파일이 아직 없는 모델을 기술한다(MODE=AIDECLARE, 기본 이미지). model.baseModels[].ref의 기반 모델과 datasets[].ref(huggingface:<owner>/<name>)의 데이터셋은 허브에서 id로 읽고, datasets[].local에는 허브에 없는 데이터를 적으며, 모델 이름과 버전은 --project와 --version을 쓴다. 내려받기 주소와 공급자를 선언하지 않으면 SPDX 문서는 초안으로 남는다. --ui(모델 · 데이터셋 화면 사용)와 --diff에는 쓸 수 없다
--no-spdx3 false AI 모델이나 데이터셋 스캔에서 SPDX 3.0.1 AI 문서와 그 검사 결과, 선언 양식을 만들지 않는다
--vex <file> — 공급사가 이 제품에 대해 보낸 CycloneDX VEX 문서(JSON). 스캔한 SBOM의 컴포넌트에 해당하는 진술을 {Project}_{Version}_vex_imported.json에 보관하며, SBOM과 보안 보고서는 바꾸지 않는다. 진술이 보안 보고서의 발견 항목에 표시되므로 --deep-cve처럼 보안 보고서도 함께 켠다. 웹 UI에서 스캔 폴더를 열면 취약점 행에서 볼 수 있다. 제품이나 버전이 다른 문서, 또는 CycloneDX VEX가 아닌 파일은 알리고 건너뛰며 스캔은 끝까지 진행한다. 적용할 진술이 없는 문서는 이전 _vex_imported.json을 그대로 둔다. --ui(취약점 화면의 “VEX 가져오기” 사용)와 --diff에는 쓸 수 없다

BSI TR-03183-2 8장처럼 빌드 산출물마다 SHA-512를 담은 distribution 유형의 externalReferences 항목도 쓴다. 이 항목의 url은 bomlens:distribution-url 속성이 있으면 그 값(http나 https URL, 또는 ..가 없는 상대 경로이며 %는 %XX 형식이어야 함)이고, 없으면 빌드 산출물 경로다. 빌드 산출물이 여럿인 컴포넌트는 파일마다 항목을 하나씩 받으며 bomlens:distribution-url을 쓸 수 없다. acknowledgement 없이 적은 라이선스는 배포 라이선스인 concluded로 기록하고, 선언 파일이 적은 acknowledgement는 그대로 둔다. 컴포넌트에는 다음 CycloneDX 필드만 쓸 수 있다. name, version, bom-ref, group, description, copyright, cpe, purl, publisher, author, mime-type, type, scope, tags, supplier, manufacturer, authors, hashes, licenses, externalReferences, properties이며, 하위 components를 포함한 그 밖의 필드는 필드 이름을 알리고 거부한다. 라이선스 id는 SPDX 라이선스 목록에 있는 식별자여야 하고 목록에 없는 식별자는 거부한다. 목록에 없는 라이선스는 name으로 적는다. 이 규칙을 어긴 파일은 거부한다. 4 MiB를 넘는 파일, bomlens:origin이 없거나 잘못된 컴포넌트, 없거나 스캔 대상 밖에 있는 파일 경로, 같은 이름과 버전을 두 번 적은 경우가 그 예다. 이때 스캔은 SBOM을 마무리하기 전에 멈추고, 그때까지 만든 SBOM을 _bom.json 대신 {Project}_{Version}_bom.refused.json으로 남긴 뒤 파일과 컴포넌트를 알리고 1로 끝난다. --target으로 준 Yocto 빌드 디렉터리에서는 빌드 산출물 대신 bomlens:yocto-recipe에 레시피 이름(PN)을 적고, 기본 파일은 읽지 않는다. 선언은 이미지에 설치된 패키지 중 빌드가 그 PN을 레시피로 기록한 패키지 전부에 적용된다. 빌드가 레시피를 기록하지 않은 패키지는 이름이 같아도 맞추지 않는다. lib32-<PN>, nativesdk-<PN> 같은 멀티립과 SDK 변형은 별도 레시피이므로 따로 선언하며, 이미지에 설치된 변형이 있으면 경고로 알린다. 각 패키지는 이름, 버전, purl, CPE를 그대로 두고, 선언한 유형, 공급자, 라이선스(concluded), bomlens:origin을 받는다. SPDX 문서가 패키지마다 기록한 파일과 해시(SHA-256, Yocto 6.1부터는 SHA-512도)는 bsi:component:filename과 함께 file 유형 하위 컴포넌트로 들어가며, 패키지 해시를 따로 만들지 않는다. 설치된 패키지가 없는 레시피, 빌드 기록과 다른 버전, bomlens:yocto-recipe와 함께 적은 bomlens:artifact, 레시피 선언에 적은 hashes, purl, cpe, bom-ref, group, mime-type, 설치된 패키지와 이름이 같은 구성요소를 이름으로 추가한 경우(그 패키지는 레시피로 선언함)도 같은 방식으로 거부한다. 어떤 스캔에서든 스캔이 직접 쓰는 속성(bomlens:identifiedBy, bomlens:yocto:recipe, bomlens:layer, bomlens:yocto:arch)은 선언 파일에 적을 수 없다. --analyze와 함께 쓰면 거부한다. 거기에 준 SBOM은 받은 SBOM이므로 바꾸지 않는다. --ui와 --diff에는 쓸 수 없다. 웹 UI는 스캔하는 폴더(소스 트리 또는 Yocto 빌드 디렉터리) 루트의 sbom-declared.cdx.json을 읽는다. 자체 구성요소 선언 가이드 참고

sbom-scanner:local처럼 레지스트리 경로가 없는 짧은 로컬 이름이나 1.13.2보다 낮은 버전 태그이면 이전 기본값을 씁니다. opt-in 이미지는 ghcr.io/sktelecom/bomlens-<이름>:latest, --deep-license는 SBOM_SCANNER_IMAGE 자체입니다.

SBOM_SCANNER_IMAGE를 digest로만 지정하면 opt-in 이미지는 CLI와 웹 UI에서 :latest를, 데스크톱 앱에서 앱 버전 태그를 씁니다. opt-in 이미지도 고정하려면 각 SBOM_*_IMAGE를 지정하세요.

BOMLENS_MAVEN_FULL_GRAPH 같은 소스 스캔 의존성 해석 옵션은 Docker 이미지 환경 변수에 정리돼 있습니다. scan-sbom.sh를 실행하는 셸에서 설정하면 같은 방식으로 의존성 해석에 적용됩니다.

Windows에서는 명령 프롬프트에서 설정한 환경변수가 더블클릭 실행에는 적용되지 않습니다. 그래서 런처는 UI_PORT, SBOM_LANG, SBOM_PULL, SBOM_IMAGE_TAR, SBOM_SCANNER_IMAGE, SBOM_OUTPUT_DIR, SBOM_UI_MOUNT_DIR을 텍스트 파일에서도 읽습니다. scripts/bomlens.settings.example.txt를 스크립트 옆에 bomlens.settings.txt로 복사하거나 %USERPROFILE%\.bomlens\settings.txt에 두면 됩니다. 실제 환경변수가 있으면 그쪽이 우선합니다.

출력 플래그 상세는 보고서 생성 가이드를, 공급사 SBOM 검증은 공급사 SBOM 검증을 참고하세요.

AI 선언 파일

Section titled “AI 선언 파일”

--ai-declare는 JSON 파일을 받습니다. AI 스캔이 만든 {Project}_{Version}_ai-declaration.template.json에서 시작해 해당하는 항목만 채우면 됩니다. 아래 예는 고객 상담 채팅 서비스에서 실행되며 외부 번역 모델을 호출하는 모델을 기술합니다.

service와 모델의 입력과 출력 종류, 학습 연산량, 적대적 시험 여부는 같은 실행에서 CycloneDX SBOM에 들어가고, 나머지 값은 SPDX 3.0.1 문서에만 들어갑니다. 키와 허용 값 전체는 선언한 AI 서비스에 있습니다. BomLens v1.13 이하는 service나 이 모델 키가 있는 파일을 “unknown key(s)” 오류로 거부합니다. --ai-declare만 입력으로 줄 때는 --no-spdx3를 함께 쓸 수 없습니다. 선언한 값 대부분이 들어갈 곳이 없어지기 때문입니다.

산출물 위치

Section titled “산출물 위치”

스캔마다 자체 {Project}_{Version}/ 하위 폴더에 격리되므로, 한 번 실행에서 나온 파일이 한곳에 모이고 CLI가 스캔하는 소스 트리를 오염시키지 않습니다. 이 하위 폴더는 베이스 디렉터리 아래에 만들어집니다.

  • CLI(scan-sbom.sh): 베이스는 명령을 실행한 디렉터리입니다. --output-dir <dir>(별칭 -o)로 바꿉니다.
  • 데스크톱 앱과 웹 UI: 베이스는 ~/sbom-output(Windows는 C:\Users\<사용자>\sbom-output)입니다. SBOM_OUTPUT_DIR 환경변수로 바꿉니다.

--git이나 아카이브 수집 시에도 클론과 해제는 종료할 때 정리되는 임시 디렉터리에서 이뤄지고, 출력 하위 폴더만 남습니다.

같은 프로젝트와 버전을 다시 스캔하면 기본적으로 그 하위 폴더를 덮어써 최신 결과만 남깁니다. 매번 따로 보관하려면 --timestamp를 붙입니다. 폴더 이름에 _YYYYMMDD-HHMMSS가 덧붙어, 예를 들어 MyApp_1.0.0_20260626-143000/가 됩니다. 이 옵션은 폴더 이름만 바꿀 뿐 SBOM 파일 이름과 내용은 그대로라서 --byte-stable과 함께 쓸 수 있습니다.

이전의 평면 배치, 즉 하위 폴더 없이 베이스에 파일을 바로 저장하던 방식으로 되돌리려면 SBOM_OUTPUT_FLAT=1을 설정합니다. 옛 경로를 기대하는 CI를 위한 옵션입니다.

--diff는 프로젝트와 버전이 따로 없으므로 실행별 하위 폴더가 아니라 베이스 디렉터리(현재 디렉터리, 또는 --output-dir)에 바로 보고서를 씁니다.

스캔이 끝날 때 출력하는 내용

Section titled “스캔이 끝날 때 출력하는 내용”

--generate-only를 쓰면 CLI가 Analysis Complete! 뒤에 만든 파일 목록을 보여 줍니다. 요청한 파일이 만들어지지 않았으면 제목이 Analysis finished with errors로 바뀌고 빠진 파일을 알리는 경고가 나옵니다. 종료 코드는 0 그대로이므로, 판정하지 못한 스캔에서 파이프라인을 멈추려면 --fail-on을 쓰십시오. 소프트웨어를 측정한 스캔(AI 모델과 데이터셋 스캔은 제외)이면 이어서 결과에 무엇이 들었는지 알려 줍니다.

숫자는 스캔 자체의 적합성 측정에서 가져오므로 적합성 검사 보고서의 licenseCoverage, softwareComponentCount 필드와 같고, purl 비율도 그 보고서의 purl 검사와 같은 패키지를 셉니다. purl 비율은 CycloneDX 결과에서만 나옵니다. 이상이 있으면 경고 줄이 뒤따릅니다.

  • No software was identified: 결과에 컴포넌트가 없습니다. 스캔한 폴더에 지원하는 생태계의 매니페스트나 lock 파일이 있는지 확인합니다.
  • No component declares a license: 라이선스를 선언한 컴포넌트가 없어서 라이선스 검사가 다룰 것이 없습니다.
  • Reduced analysis: 전체 분석 대신 얕은 대체 분석이 돌아 직접 의존성만 식별했습니다. 원인(디스크 부족, 메모리 부족, 내려받기 실패, 의존성 분석기의 실패 또는 미실행)을 함께 보여 줍니다.
  • Steps that failed: 끝내지 못한 후처리 단계의 이름입니다. 자세한 내용은 위쪽 로그에 있습니다.

마지막 두 줄은 이번 실행이 아니라 제출된 문서의 이력을 말하게 되므로 --analyze에서는 나오지 않습니다. 이 요약은 종료 코드를 바꾸지 않습니다. 이런 조건에서 실행을 실패시키려면 --fail-on empty-result나 --fail-on license-coverage=<0-100>을 씁니다. 요약을 지원하기 전의 스캐너 이미지는 파일 목록만 출력합니다.

종료 코드

Section titled “종료 코드”
코드 의미
0 스캔 성공
1 스캔 실패(잘못된 인자, Docker 미실행, 필수 입력 누락 등)
2 --fail-on-conformance: 스캔은 성공했지만 적합성 검사 보고서가 “fail”
3 --fail-on-conformance: 스캔은 성공했지만 판정할 적합성 검사 보고서가 안 만들어짐
4 --fail-on: 스캔은 성공했지만 조건 하나 이상에 걸림
5 --fail-on: 스캔은 성공했지만 조건을 판정할 수 없음(예: 취약점 데이터베이스를 내려받지 못함, --license 없이 license-conflict, 적합성 검사 보고서가 없거나 SBOM 형식을 측정하지 못했을 때의 empty-result와 license-coverage=), 또는 판정할 결과가 안 만들어짐

2부터 5까지는 해당 옵션을 줬을 때만 나오며, 둘 다 쓰지 않은 스캔은 0 또는 1로 끝납니다. --fail-on 조건은 각각 판정 결과와 함께 출력합니다. 둘 이상의 코드가 해당하면 작은 쪽이 우선합니다. 적합성(2, 3)이 4보다, 조건에 걸림(4)이 판정 불가(5)보다 먼저입니다. 판정 불가를 실패로 처리하는 것은 의도한 동작입니다. 살펴보지 못한 스캔은 아무것도 발견하지 못한 스캔과 다르므로, 취약점 데이터베이스가 없는 폐쇄망 실행이 vulnerability= 게이트를 우연히 통과하는 일이 없습니다.

소스 트리에 남은 중단된 빌드 산출물

Section titled “소스 트리에 남은 중단된 빌드 산출물”

소스 스캔(--target <디렉터리>, 웹 UI의 폴더 스캔, 데스크톱 앱)은 스캔한 트리에 빌드 단계(cargo generate-lockfile, go mod tidy, npm install 등)를 실행한 뒤 원래 상태로 되돌립니다 - 빌드 단계가 바꾸거나 새로 만든 파일은 모두 복원되거나 지워집니다. 그 스캔이 강제 종료, 메모리 부족 종료, 호스트 크래시로 끝나면 이 복원이 실행되지 못해 변경 사항이 그대로 남습니다. 같은 소스 트리를 다시 스캔하면, 이전 스캔의 컨테이너가 더는 실행 중이지 않은 것을 확인한 뒤 다른 무엇보다 먼저 그 복원부터 마칩니다.

재스캔 시 출력 폴더에 남은 산출물

Section titled “재스캔 시 출력 폴더에 남은 산출물”

같은 --project/--version으로 다시 스캔하면 이전 스캔이 어떻게 끝났든 같은 출력 폴더를 재사용합니다. 새 스캔은 자신의 산출물을 쓰기 전에, 오늘의 모드나 옵션으로는 만들지 않을 BomLens 자신의 파일을 먼저 지웁니다. 그래서 옵션이 달랐던 이전 실행의 산출물이 이번 실행의 결과로 착각될 일이 없습니다. 직접 폴더에 둔 파일이나 다른 버전의 산출물은 그대로 남습니다.
