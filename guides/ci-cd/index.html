Use in CI/CD

An SBOM is a point-in-time snapshot of dependencies, so it must be regenerated whenever dependencies change to stay in sync with the code. In CI it refreshes on every build and release, attaches to release artifacts, and becomes the basis for a vulnerability policy gate.

Important: a scan reports vulnerabilities and exits successfully unless you ask it to gate. --fail-on makes the scan itself exit non-zero when a condition you name is met (exit 4), or cannot be judged from what the scan produced (exit 5): a finding at a severity or worse, a known malicious package, a license conflict, a scan that found no software (empty-result), or license coverage below a percentage you set (license-coverage=<0-100>). --fail-on-conformance does the same for the conformance check report (exit 2). See Exit codes. No separate step that inspects the report files is needed.

To reduce load, split depth by trigger: on PRs generate the SBOM quickly (--generate-only --no-report); on main and releases generate everything (--all --generate-only) and apply the gate.

Declared components in CI

Section titled “Declared components in CI”

Your own executables, libraries and firmware, and the vendor binaries or copied sources a scan cannot find, are listed in a declaration file kept in the repository (see Declaring your own components). The scan reads the build outputs that file names, so the job builds first and scans after. This release job also checks the result against BSI TR-03183-2 and takes the version from the tag.

${GITHUB_REF_NAME#v} turns the tag v2.1.0 into 2.1.0, which a first-party component without its own version takes. --components names the file explicitly; without it, sbom-declared.cdx.json at the repository root is read anyway. --license takes an SPDX identifier.

When the runner has no Docker

Section titled “When the runner has no Docker”

scan-sbom.sh starts containers, so it needs a Docker engine: a runner without one (a Kubernetes runner, a GitLab job without docker:dind) cannot use the examples above. Run the scanner image itself as the job image instead. A source scan inside it needs no Docker socket when a lock file covers the whole tree (a package-lock.json, npm-shrinkwrap.json, pnpm-lock.yaml, bun.lock or gradle.lockfile, with no other manifest below the root): it reads the lock file as it is and fills the licenses it lacks from the package registry. A tree without such a lock file is read by syft from its manifests, which gives direct dependencies only (a Node project with none is refused with guidance), so commit a lock file or use a runner that has Docker.

The variables are the ones of the direct docker run; the scan reads the project from SOURCE_ROOT and writes into the folder it runs in.
