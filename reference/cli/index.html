CLI reference

Full options, analysis modes, CI/CD integration, and troubleshooting for BomLens.

Options reference

Section titled “Options reference”

Windows: the commands here are for macOS/Linux. Pick one of the following. See Getting started for installation.

  • Replace ./scripts/scan-sbom.sh with scripts\scan-sbom.bat (needs Git Bash).
  • Under WSL2, run the commands as-is.
  • To work without a command line, double-click scripts\sbom-ui.bat, or download the desktop app.
Option Default Description
--project <name> — (required) Project name
--version <version> — (required) Project version
--supplier <supplier> — The supplier of the product this SBOM describes, written as "Name <https://...>" (recorded as its url) or "Name <email>" (recorded as a contact email), in metadata.component.supplier; "<https://...>" without a name records only the URL. A value that is empty after trimming writes nothing. metadata.supplier is left alone, since it would read as the SBOM’s author. A bare name is recorded with a warning, since the bsi-tr-03183-2 profile needs a URL or email for it. Not written under --analyze, which keeps the supplier’s own SBOM as it is; a Yocto build directory given as --target is scanned through the same path but its SBOM is this scan’s, so it is written there
--target <target> current directory What to analyze: a directory (source tree, or an OS rootfs / staging build output), a Docker image, a binary file, or a .zip/.tar.gz archive. A Yocto build directory is recognized as such, and the image SBOM it published under tmp/deploy/images/ is analyzed instead of the build tree being walked (see the supplier SBOM guide). A folder that is not a source tree (no manifest, lockfile or build file at its top level) and directly holds one root filesystem or one firmware image (by signature or a firmware extension such as .bix or .trx; .bin and .img by signature only), such as a release images/ folder, is scanned as that root filesystem or image, and the scan says so. A folder with executables, shared libraries, node_modules or model files at its top level, or more than 20 top-level files, stays a source scan. When it holds several, the scan stops and lists the --target to use for each
--git <url> — Shallow-clone a git/GitHub URL and analyze it as source (private repos: GIT_TOKEN env var)
--branch <ref> default branch Branch, tag, or commit of the --git target (alias --ref)
--exclude <path> — Leave a path out of a source scan. Repeatable. The path is relative to the scanned folder (for example --exclude vendor/legacy); globs, absolute paths and .. are rejected. The scan runs on a copy of the tree without the excluded paths, so the build, the license scan and the file tree all skip them. A path that does not exist is reported and ignored
--firmware false Force firmware mode on the --target file, or on a --target folder holding an unpacked image such as a root filesystem from the build (opt-in firmware image). A root filesystem folder with no package database switches to it on its own when the firmware image is present
--as-source false Scan a directory --target as a source tree, as it is: no switch to a root filesystem or firmware image the folder holds, and no Yocto build directory or root filesystem recognition. Cannot be combined with --firmware
--analyze <sbom> — Validate and analyze a supplier SBOM (alias --sbom). CycloneDX/SPDX. Mutually exclusive with --target
--model <ref> — Generate an AI SBOM (CycloneDX 1.7 ML-BOM). A HuggingFace model id (owner/name) goes through the OWASP AIBOM Generator (opt-in bomlens-aibom image; fetches model-card metadata over the network). A Figshare item — its page URL, its DOI, or the item number — is described as a dataset from the public item endpoint, with no account and no opt-in image; an institutional DOI that does not carry “figshare” cannot be told apart from any other DOI, so give the item URL for those. A HuggingFace dataset, given as datasets/<owner>/<name>, as https://huggingface.co/datasets/<owner>/<name> (anything after the name, such as /tree/main, is ignored) or as hf:<owner>/<name>, is described as a dataset in the base image, and the datasets its card lists under source_datasets are read too (AIBOM_DATASET_DEPTH, AIBOM_DATASET_MAX_LOOKUPS). A bare owner/name is always a model id, because the hub uses the same form for both. A gated or private dataset needs HF_TOKEN. Mutually exclusive with --target/--analyze/--git/--merge
--model-file <path> — Read one AI model file and describe it from its own header: GGUF, safetensors, PyTorch (.pt/.pth/.ckpt), pickle, npz, npy or ONNX. Offline, no HuggingFace account, and it works on a model that was never published. What can be filled depends on the format — GGUF carries a name, a license and an architecture, while safetensors usually carries only tensor shapes, and a field the file does not declare is left empty rather than guessed. A .gguf/.safetensors/.pt/… path passed to --target is read this way too. Mutually exclusive with --target/--analyze/--git
--license <spdx-id> — The outbound license the project is distributed under (e.g. Apache-2.0). Recorded on the SBOM’s root component, with acknowledgement concluded (the distribution licence), and used to flag dependencies whose terms clash with it. It replaces a root license the generator read. A source scan cannot infer this — cdxgen leaves the root license empty for maven and gradle — so without it no conflict verdict is produced; a license read from the project manifest instead only fills an empty root license, as declared. A supplier SBOM’s own root license under --analyze is never replaced; for a Yocto build directory given as --target it is recorded on the image. An SPDX License List id (in any letter case) is written as license.id, a LicenseRef- or DocumentRef-...:LicenseRef- name (prefixes in any letter case) as license.name, and an expression as expression: SPDX ids and LicenseRef- names joined by AND or OR, WITH followed by an SPDX exception id, and balanced parentheses, with operators in any letter case and ids written in the SPDX list’s spelling. Anything else, free text such as Proprietary or an expression such as Proprietary or commercial or MIT AND, is refused with the reason and, for free text, the LicenseRef- name to use. In the scans that record it (a source scan, a root filesystem, a Yocto build directory) it is refused when the scan starts, before anything is generated, whoever started it (CLI, web UI or a CI job); the CLI refuses it before starting a container. A licence read from the project manifest that does not fit is left out with a warning
--sbom-author <name> — The entity that generated the SBOM — the organisation or person running the scan, not the tool and not whoever wrote the software. Recorded in metadata.authors, using the full name without acronyms. Nothing in a scan can discover it, so the field is left out of the SBOM when it is not given rather than filled with a placeholder. Written as Name <email> (for example "Example Corp <sbom@example.com>"), the email is recorded too, as the bsi-tr-03183-2 profile asks of the SBOM creator. Not written under --analyze, except for a Yocto build directory given as --target, whose SBOM this scan generates
--ai-declare <file> — For an AI model or dataset scan: the publisher’s declaration (JSON) of what a scan cannot read, such as release dates, who made the model and the data, which datasets trained or tested it, the base model revision and the distributed weights scope. Most declared values are written only to the SPDX 3.0.1 AI document. The exceptions are the service the model runs in (service) and the model’s input and output kinds, training compute and adversarial testing, which also go into the CycloneDX SBOM, marked as the publisher’s declaration (see the example below). Every AI scan writes an empty one to start from, {Project}_{Version}_ai-declaration.template.json. A file that names a field, value, dataset or base model the scan does not have is refused with the reasons, and the document is written without it, as a draft. The accepted file is kept as {Project}_{Version}_ai-declaration.json and applied again on the next scan of the same version. Given alone, without --model, --model-file or --target, it describes a model that has no hub repository or file yet (MODE=AIDECLARE, base image): the base models in model.baseModels[].ref and the datasets in datasets[].ref (huggingface:<owner>/<name>) are read from the hub by id, datasets[].local lists data the hub does not hold, and the model is named by --project and --version. Without a declared download address and supplier, the SPDX document stays a draft. Not offered with --ui (use the Models & datasets screen) or --diff
--no-spdx3 false For an AI model or dataset scan: do not write the SPDX 3.0.1 AI document, its check or the declaration template
--vex <file> — A CycloneDX VEX document (JSON) a supplier sent for this product. The statements that apply to a component of the scanned SBOM are kept in {Project}_{Version}_vex_imported.json; the SBOM and the security report are not changed. Turns the security report on too (as --deep-cve does), because the statements are shown on its findings: open the scan folder in the web UI to see them on the vulnerability rows. A document for a different product or version, or one that is not CycloneDX VEX, is reported and skipped, and the scan still completes; a document with no applicable statement leaves an earlier _vex_imported.json as it was. Not offered with --ui (use Import VEX on the Vulnerabilities screen) or --diff
--component-versions <file> — For a firmware, root filesystem or binary scan: a CSV file, name,version,reason, giving the version of components the scan found but could not read a version for. The third column is optional (a two-column name,version file is read as before); with the version left empty it says why there is none: own-code, not-open-source or version-unknown, recorded on the component as bomlens:versionReason. A reason on a row that also has a version, on a component the scan read a version for, or on a name the scan did not find is ignored with a warning. A version the scan read from the delivered files is kept and a warning shows both; a name the scan did not find is added as a component marked bomlens:identifiedBy = supplier-declared. Every such scan writes the components still missing a version to {Project}_{Version}_component-versions.template.csv in this format. A file over 256 KiB, with a malformed row or with any other reason value is refused: the scan still writes its files, without those versions, and exits 1 with the reason. A row with neither a version nor a reason is skipped. See the firmware guide
--binary-kb <path> — For a firmware, root filesystem or binary scan: a binary knowledge base (the kb.sqlite3 file, or the folder that holds it) built from the release sources of the components to look for. It finds what left no version string and no package record behind, such as a library linked into a program. A component gets a version only when exactly one release in the base fits; with several, it is reported without a version and bomlens:versionCandidates lists them. A result whose one fitting release is the newest the base has is reported without a version, with bomlens:versionMayBeNewer. The base is opened read-only and never replaces a version another pass already read. A path that holds no base is refused. Not offered with --ui or --diff. See the firmware guide
--kb-decisions <file> — With --binary-kb: a JSON list of what a person decided about the base’s results, each entry {"component", "decision", "version", "reason", "reviewer", "evidence_sha256"} with decision one of exclude, confirm or version. An entry without a reason is ignored with a warning. With evidence_sha256 it applies only while the file the result was found in still has that hash. A file over 1 MiB is refused
--components <file> sbom-declared.cdx.json at the scan target root, when it exists For a source scan or a Yocto build: a CycloneDX file (JSON) listing the components the scan cannot find, such as your own build outputs and third-party parts added by hand. Repeat the option for several files; with it, sbom-declared.cdx.json is not read. Each component needs the property bomlens:origin (first-party or third-party), and a third-party one needs a version; a first-party one without a version takes --version. A build output named in bomlens:artifact (a path relative to the scan target root) gets its SHA-512 and SHA-256 hashes and the bsi:component:filename, bsi:component:executable, bsi:component:archive and bsi:component:structured properties (structured or unstructured as BSI TR-03183-2 defines it), read from the file; a value the declaration gives for executable, archive or structured is kept instead. Each build output is also named on an externalReferences entry of type distribution carrying its SHA-512, as BSI TR-03183-2 section 8 does: its url is the component’s bomlens:distribution-url property when given (an http or https URL, or a relative path without .., in which a % must start a %XX escape), otherwise the build output’s path; a component with several build outputs gets one per file and cannot give bomlens:distribution-url. A licence given without an acknowledgement is written as concluded, the distribution licence; an acknowledgement the declaration gives is kept. A component may use only these CycloneDX fields: name, version, bom-ref, group, description, copyright, cpe, purl, publisher, author, mime-type, type, scope, tags, supplier, manufacturer, authors, hashes, licenses, externalReferences and properties; any other field, nested components included, is refused by name. A license id must be an id on the SPDX License List, so an unknown id is refused; give a license that is not on the list as name. A file that breaks these rules is refused, for example one over 4 MiB, a component without a valid bomlens:origin, a named file that is missing or outside the scan target, or the same name and version declared twice: the scan stops before the SBOM is finished, keeps the SBOM written so far as {Project}_{Version}_bom.refused.json (not _bom.json) and exits 1, naming the file and component. For a Yocto build directory given as --target, a component names its recipe (PN) in bomlens:yocto-recipe instead of a build output, and no default file is read: the declaration goes on every package installed in the image whose recipe the build recorded as that PN (a package whose recipe the build did not record is not matched by its name; a multilib or SDK variant such as lib32-<PN> or nativesdk-<PN> is a recipe of its own, declared separately, and a warning names any the image installs), which keep their name, version, purl and CPE and get the declared type, supplier, licence (concluded) and bomlens:origin. The files and hashes the SPDX document records for each package (SHA-256, and SHA-512 from Yocto 6.1) are nested under it as file components with their bsi:component:filename; no package hash is made up. A recipe that installed no package, a version other than the build’s, bomlens:artifact beside bomlens:yocto-recipe, hashes, purl, cpe, bom-ref, group or mime-type on a recipe declaration, or a component added by name that has the name of an installed package (declare that one by its recipe), is refused the same way. In any scan a declaration may not carry the properties the scan itself writes (bomlens:identifiedBy, bomlens:yocto:recipe, bomlens:layer, bomlens:yocto:arch). Refused with --analyze: an SBOM passed there is received, and is not changed. Not offered with --ui or --diff; the web UI reads sbom-declared.cdx.json at the root of the folder it scans, a source tree or a Yocto build directory. See the declared components guide
--no-components false For a source scan: do not read sbom-declared.cdx.json at the scan target root, for example in a scan made before the build outputs it names exist. When that file is refused because a build output is missing, the message points to this option. Cannot be combined with --components; not offered with --ui (the web UI’s Read sbom-declared.cdx.json switch does the same) or --diff
--usage <scenario> — Tailor the AI model risk assessment (--model and --model-file) to how the model will be used: internal, product, redistribute or outputs-only. Only the license conditions that bind that scenario decide the verdict, and the report states which scenario it was judged for. Unset judges against every condition
--merge <a.json> <b.json> … — Merge two or more CycloneDX SBOMs into one, dedupe by purl, and stamp the root component with --project/--version. Optional — for a server SBOM when an external system needs a single product BOM; otherwise keep the layers separate (see the server SBOM guide). Mutually exclusive with --target/--analyze/--git
--merge-root <file> — With --merge: keep this input’s specVersion and root component (for example an ML-BOM’s CycloneDX 1.7 root with its model card) instead of writing a fresh root at the --spec-version version. Must be one of the --merge files; the preserved root is renamed to --project/--version
--diff <old.json> <new.json> — Compare two already-generated AI-model SBOMs (--model or --model-file output) for drift: a bomlens:assessment:* verdict that got worse, a changed declared license, or a SHA-256 weight-file hash that no longer matches under the same model name/purl/HuggingFace id — the last one means the artifact behind a stable name silently changed. Needs neither --project/--version nor a scan target: it only reads the two files and writes <new>_model-diff.json next to the newer one (or under --output-dir)
--generate-only false Save locally only, without uploading
--upload-target <target> dependency-track Upload destination: dependency-track (DT-compatible) or trusca (native ingest)
--trusca <project_id> — Upload to TRUSCA (= --upload-target trusca + project id). Needs API_URL and a Bearer API_KEY
--notice forced on by the risk-report default Generate the open-source notice (NOTICE, txt+html). The flag itself defaults to off; it is the risk report (on by default) that turns it on, so --no-report, not simply omitting --notice, is what skips it
--security forced on by the risk-report default Generate the Trivy security report (json+md+html), including CVSS, EPSS, and CISA KEV priority signals. Same mechanism as --notice: --no-report skips it, omitting the flag alone does not
--spdx false Also export the SBOM as SPDX 2.3 JSON (_bom.spdx.json), converted from the final CycloneDX output
--spec-version <1.6|1.7> 1.6 CycloneDX version of the SBOM. 1.7 has cdxgen and syft write 1.7, and an SBOM put together at 1.4, 1.5 or 1.6 is labelled 1.7, $schema included, before it is delivered. Those versions only gained fields up to 1.7, except that from 1.6 on a property must have a name, so a 1.4 or 1.5 property without one is removed as the SBOM is raised. An SBOM at 1.3 or older keeps its version, and so does a 1.4 SBOM at the default 1.6, which then gets no metadata.lifecycles (a 1.5 field). NOTICE, the security report, the conformance check and the web UI read either version. AI model and dataset SBOMs are 1.7 whatever this says. Dependency-Track reads 1.7 from 4.14.4 and 5.1.0 on; an older server, or one whose version is not known, that refuses it gets a 1.6 copy (see Upload). Any other value stops the scan
--all — --notice --security --spdx
--no-report false Skip the open-source risk report (see below)
--lang <en|ko> en Language for the human-facing conformance and AI-profile reports (.md/.html). The SBOM and the JSON reports stay English regardless
--conformance-profile <default|skt-submission|bsi-tr-03183-2> default Conformance check strictness. skt-submission requires 100% PURL coverage and fails on any pkg:generic identifier, matching the SKT supplier submission review. It also adds a required “Version needed” row, which fails only on components with neither a version nor a reason (fill them with --component-versions) and lists the ones with a reason as explained by the supplier, and an advisory “No upstream purl” row for versioned components without an upstream purl, which SK Telecom checks separately. For a firmware, root filesystem, binary or Yocto build directory scan, and under --analyze for an SBOM marked bomlens:scanMode by one, the name+version, PURL coverage, pkg:generic and transitive-dependency rows warn instead of failing on what those two rows already cover, since such a scan records packages found rather than a dependency graph. The profile accepts pkg:sourceforge and pkg:gnu, and says in the summary that {Project}_{Version}_bom.json is the one file to submit. The web UI’s submission-review screen defaults to skt-submission; the CLI does not, so pair it with --analyze explicitly. In every profile, a component the --components file added in this scan with bomlens:origin first-party, a supplier and a SHA-512 needs no purl: it is left out of PURL coverage, the pkg:generic row and the upstream-purl row, and listed on an advisory row by name. A third-party one is not, and nothing is exempted under --analyze. bsi-tr-03183-2 measures the SBOM against BSI TR-03183-2 v2.1.0: CycloneDX 1.6 or later (SPDX 3.0 or later), a timestamp, an SBOM creator with an email or URL (metadata.manufacturer, or metadata.authors with an email, which --sbom-author "Name <email>" writes), and a dependency graph that reaches every component from the product are required; the graph row warns when the SBOM does not state its completeness (compositions), and a component without its own dependencies entry is listed on an advisory row. The product (metadata.component) needs a creator with a URL or email, a name, a version and a concluded licence (--license writes the licence and --supplier the creator), and its filename, SHA-512 and file properties when it names a file. For each component the --components file added, the creator (supplier or manufacturer with a URL or email), name and version, and the distribution licence as an SPDX identifier, expression or LicenseRef- name with acknowledgement concluded are required; for one that names a build output, so are its file name, SHA-512 (on the component, its files or a distribution reference) and executable, archive and structured properties. A declared library or framework with no file of its own is listed on an advisory row; a declared component of any other type without one fails the file rows. The components the scan found are measured on one advisory row, with counts and each component’s gaps, and do not move the result; in the SBOM a scan generated from a Yocto build directory, a SHA-512 missing from a package the build recorded is reported there as not in the source SBOM. For such a package declared by recipe (bomlens:yocto-recipe), a SHA-512, file name or file properties the build did not record are reported the same way on the declared rows, as a warning rather than a failure. A received SBOM (--analyze) gets no such allowance, whatever properties its components carry. PURL coverage is advisory in this profile
--license-registry off Ask the package registry (deps.dev) for the licence of a component that has none, and check a component’s single strong-copyleft or non-commercial licence (GPL, AGPL, SSPL, BUSL, CC-BY-NC) against it. When the registry says otherwise its answer replaces the recorded one, and the old value is kept in bomlens:license:superseded; licences written this way carry bomlens:licenseSource = registry (deps.dev). A licence with its text, a url or a concluded acknowledgement is never checked, and with --analyze only missing licences are filled. Uses the network
--resolve-purl off --analyze only: ask each package repository whether the identifiers in the submitted SBOM name packages that exist, and add the answer to the conformance check report as an advisory row. The only part of the check that uses the network. An identifier that resolves to nothing is reported, never failed, because a package published only to an internal repository answers the same way; PURL_RESOLVE_IGNORE skips namespaces you know are internal
--analyze-cpe-index off --analyze only: match the components of a BomLens-generated SBOM that carry bomlens:purlSource=upstream-map against the bundled CPE index, as a generating scan does. Other components are not matched. The property is plain text in the file, so an edited SBOM can lose it, and a component whose CPE was removed is not found.
--deep-license false Precise license detection with scancode in the project’s own files (opt-in bomlens-deep-license image, pulled automatically; when it cannot be pulled, the scan runs on the base image without the licence scan). With --deep-cve as well, the licence scan runs first in this image and post-processing then runs on the deep-cve image, so both _scancode.json and _security_grype.json are written
--deep-cve false Add a second CVE-matching pass via grype’s NVD CPE matcher (opt-in bomlens-deep-cve image, pulled automatically; a source scan runs its post-processing step on it, and when it cannot be pulled, the source scan goes on without the grype match; with a SBOM_SCANNER_IMAGE that is a local build, a version before 1.13.2 or another name and no SBOM_DEEP_CVE_IMAGE, post-processing stays on that image, which runs the match only if it has grype, also with --deep-license). Recovers NVD-only CVEs that Trivy misses, mostly for older Maven libraries, since BomLens attaches an NVD-matchable CPE to Maven components specifically; implies --security. Findings not verified against the live NVD version range are flagged version-unverified in the report. See the deep CVE matching guide
--reachability false Go source, or a Go executable given with --target: judge with govulncheck whether the code each Go advisory names is reached, from the source’s call graph or from the executable’s symbols. An advisory whose code is not reached is recorded as not_affected (with code_not_present when the affected package is not in the build, code_not_reachable when it is but no affected function is reached) in {Project}_{Version}_reachability.cdx.json (CycloneDX VEX), marked on its finding in _security.json, listed in its own “Not reachable” section of the security report, and left out of that report’s totals, the risk report’s and --fail-on vulnerability=. One whose code is reached is exploitable, with the call path. Implies --security. govulncheck reads the Go vulnerability database (vuln.go.dev) over the network; when it cannot, the step is skipped and the report is as without the option. A source scan runs govulncheck in the Go image of stage 1, for each Go module in the tree (up to 20) and for GOOS linux, darwin and windows (GOARCH amd64) with the default build tags; code built only under a custom build tag is not covered. With --ui it is chosen per scan in the web UI’s advanced scan options instead. See Go reachability
--identify-vendored false Identify open source copied (vendored) into C/C++ source that has no package manager. Matches file fingerprints against the OSSKB service (included in the published image; sends hashes, not source). See the identify bundled OSS guide
--verify-weights false With --model: download the repo’s pickle-format weight files (.bin/.pt/.pth/.ckpt — the ones that execute code on load) and run the same local picklescan verification --model-file runs, instead of only trusting HuggingFace’s own scan (bomlens:hf:scan:*). safetensors/GGUF/ONNX weights are never downloaded — they cannot execute code on load, so there is nothing for picklescan to check. Real network and disk cost (bounded by AIBOM_VERIFY_MAX_FILES/AIBOM_VERIFY_MAX_BYTES, default 5 files / 2 GiB each), unlike the metadata-only ENRICH_HF_SECURITY lookup, which is why this is opt-in. AI-model scans only
--byte-stable false Deterministic (reproducible) SBOM output
--detection <how> auto How a source scan finds its dependencies: build resolves them in a cdxgen language image, static reads the lock file and does not build (no language image to pull, about 5 to 10 seconds shorter; a project with no complete lock file comes out short, a workspace takes its members’ dependencies in, and the copyright notices a build reads from downloaded packages, for example 73 of 98 crates in a Rust project, are not filled), auto reads statically only when a package-lock.json, npm-shrinkwrap.json, pnpm-lock.yaml, bun.lock or gradle.lockfile covers the whole tree and builds otherwise. A static scan fills the licenses a lock file does not carry from the package registry (the same lookup as --license-registry), so auto builds under --byte-stable or FETCH_LICENSE=false. DETECTION=<how> in the environment does the same. The SBOM records which way it was made (bomlens:detection)
--fail-on-conformance false Exit 2 if this scan’s own conformance check report says “fail” (exit 3 if no conformance check report was produced for this scan). Not offered with --ui. See Exit codes
--fail-on <condition> — Exit 4 when this scan meets the condition, or 5 when it cannot be judged from what the scan produced. Repeat the option for several conditions. The conditions are a closed list: vulnerability=<critical|high|medium|low> (a finding at that severity or worse; turns the security report on), malicious-package (a component flagged as a known malicious package), license-conflict (a component incompatible with the license the product is distributed under; the SBOM’s root component has to record it, which --license does for source and rootfs scans and a supplier SBOM carries itself, otherwise it cannot be judged), empty-result (the scan identified no software: no component is left once operating-system and file entries are set aside, so a rootfs or image scan that names no package counts as empty), license-coverage=<0-100> (fewer than that percent of those same components declare a license; a license of NOASSERTION or NONE is not a declaration, and the percentage is rounded down; the value is required, has no default and takes no leading zero). Both read the scan’s own conformance check report, so a scan that wrote none cannot be judged, nor can one whose SBOM format the report did not measure (an SPDX 3.0 document that could not be converted). license-coverage= cannot be judged on a scan with no such component either (use empty-result for that). They leave the conformance verdict itself unchanged. Findings are counted as the security report counts them: once per package and id, with the kernel’s advisories left out. --vex statements are not applied, so a finding the supplier declared not affected still counts; a finding --reachability judged not reachable does not. vulnerability= is not available for AI model and dataset inputs, which have no dependencies to scan, and neither is empty-result. Not offered with --ui or --diff. See Exit codes
--sign false cosign signature (COSIGN_KEY required)
--output-dir <dir> current directory Base directory for outputs (alias -o). Each scan lands in a {Project}_{Version}/ subfolder under it, keeping the bundle together and out of the source tree
--timestamp false Append _YYYYMMDD-HHMMSS to the run subfolder so repeat scans of the same project and version are kept side by side instead of overwritten. Folder name only; SBOM bytes are unchanged
--ui — Launch the local web UI
--mount <dir> — With --ui: expose an extra host directory to the web UI as a read-only target for the Directory path input (repeatable). Lets the UI scan an OS tree outside the launch folder — including the running host OS with --mount /. Results still save under the launch folder
--help — Print help

ANALYZE mode (--analyze) is an exception to six of these. --project/--version/--license/--sbom-author/--supplier never overwrite what a supplier’s own SBOM already declares: its existing name, version, root license, authorship and supplier are a fact about the document, not something this run has the authority to replace. --no-report has no effect because the risk report is always generated for a supplier SBOM under review. When the submitted SBOM is missing one of these fields outright (no root license, no metadata.authors, no product supplier), the flag still cannot fill it in; the field stays empty and the conformance check judges accordingly.

Where outputs go

Section titled “Where outputs go”

Each scan is isolated in its own {Project}_{Version}/ subfolder, so the files from one run stay together and the CLI never litters the source tree it scans. That subfolder is created under a base directory:

  • CLI (scan-sbom.sh): the base is the directory you ran the command in. Override it with --output-dir <dir> (alias -o).
  • Desktop app and web UI: the base is ~/sbom-output (C:\Users\<you>\sbom-output on Windows). Override it with the SBOM_OUTPUT_DIR environment variable.

For --git or archive ingestion the clone or extract happens in a temp directory that is cleaned up on exit, and only the output subfolder remains.

A re-scan of the same project and version overwrites its subfolder by default, keeping just the latest result. Add --timestamp to keep each run instead: it appends _YYYYMMDD-HHMMSS to the folder name, for example MyApp_1.0.0_20260626-143000/. The flag changes the folder name only, not the SBOM file names or bytes, so it works together with --byte-stable.

To restore the previous flat layout, where every file is written directly in the base with no per-run subfolder, set SBOM_OUTPUT_FLAT=1. This is meant for CI that expects the old paths.

--diff has no project or version of its own, so it writes its report directly into the base directory (current directory, or --output-dir) rather than a per-run subfolder.

What the scan prints at the end

Section titled “What the scan prints at the end”

With --generate-only, the CLI lists the files it produced after Analysis Complete!. If a requested file was not produced, the heading reads Analysis finished with errors instead and a warning names the missing files; the exit code stays 0, so use --fail-on to stop a pipeline on a scan that could not be judged. For every scan that measured software (not an AI model or dataset scan) it then states what the result holds:

The numbers come from the scan’s own conformance measurement, so they match the licenseCoverage and softwareComponentCount fields of the conformance check report, and the purl share counts the same packages as its purl check. The purl share is shown for CycloneDX results only. A warning line follows when something is off:

  • No software was identified: the result has no components. Check that the scanned folder holds a manifest or lock file for a supported ecosystem.
  • No component declares a license: no component declares one, so license checks have nothing to work with.
  • Reduced analysis: a shallow fallback ran instead of the full analysis and only direct dependencies were identified. The line names the cause: out of disk space, out of memory, a failed download, or the dependency analyzer failing or not running.
  • Steps that failed: post-processing steps that did not complete, by name. Details are in the log above.

The last two are not shown for --analyze, because they would describe the submitted document rather than this run. The summary does not change the exit code. To fail a run on these conditions, use --fail-on empty-result or --fail-on license-coverage=<0-100>. A scanner image that predates the summary prints only the file list.

Exit codes

Section titled “Exit codes”
Code Meaning
0 Scan succeeded
1 Scan failed (bad arguments, Docker unavailable, a required input missing, and similar)
2 --fail-on-conformance: the scan succeeded, but its own conformance check report says “fail”
3 --fail-on-conformance: the scan succeeded, but produced no conformance check report to judge
4 --fail-on: the scan succeeded, but at least one condition is met
5 --fail-on: the scan succeeded, but a condition could not be judged (for example the vulnerability database could not be downloaded, license-conflict without --license, or empty-result and license-coverage= when the scan wrote no conformance check report or the report did not measure the SBOM’s format), or the scan produced no result to judge

2 to 5 are used only when the matching option is given; every scan that uses neither exits 0 or 1. Every --fail-on condition is printed with its verdict. When more than one code applies, the lowest wins: 2 and 3 (conformance) before 4, and 4 (a condition is met) before 5 (a condition could not be judged). “Could not be judged” is a failure on purpose: a scan that could not look is not a scan that found nothing, so an air-gapped run with no vulnerability database never passes a vulnerability= gate by accident.

Troubleshooting

Section titled “Troubleshooting”

Windows: no outputs appear

Section titled “Windows: no outputs appear”

If the scan finishes but no output files show up, check that the folder you ran from is inside a Docker file-sharing path. Anything under your home directory (C:\Users\...) is shared by default in both Rancher Desktop and Docker Desktop. From an unshared location the container cannot write results to the host.

Docker permission error (Linux/WSL2)

Section titled “Docker permission error (Linux/WSL2)”

Does not apply on Windows/macOS with Rancher Desktop or Docker Desktop. Add your user to the docker group.

Out of disk space

Section titled “Out of disk space”

Prune the Docker cache. From a terminal:

With Rancher Desktop or Docker Desktop, the same cleanup is also available from the app’s own Preferences screen.

Interrupted build artifacts in the source tree

Section titled “Interrupted build artifacts in the source tree”

A source scan (--target <dir>, the web UI’s folder scan, or the desktop app) runs build steps (cargo generate-lockfile, go mod tidy, npm install, and the like) against the scanned tree, then restores it: every file a build step changed or added is put back or removed. If that scan ends by SIGKILL, an out-of-memory kill, or a host crash, the restore never runs and the changes stay. The next scan of that same source tree restores them first, before doing anything else, once it has confirmed the earlier scan’s container is no longer running.

Leftover output-folder artifacts on re-scan

Section titled “Leftover output-folder artifacts on re-scan”

Re-scanning the same --project/--version reuses its output folder, however the earlier scan there ended. Before writing its own artifacts, the new scan removes any of BomLens’s own files under that project/version that today’s mode or options will not produce, so nothing from an earlier run with different options survives to be mistaken for this run’s output. A file you placed in the folder yourself, or a different version’s artifacts, is left alone.

Anything else

Section titled “Anything else”
  1. Run the same command again and read the terminal output. The [WARN] and [ERROR] lines say what was skipped or what failed.
  2. Update the Docker image: docker pull ghcr.io/sktelecom/bomlens:latest.
  3. If it still fails, open a GitHub Issue with the command you ran and its terminal output. The issue form lists what it needs.
